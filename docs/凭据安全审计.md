# 咕嘎凭据安全审计（API Key 会不会泄露）

> 审计日期：2026-11-08  
> 审计方式：只读审计。没有修改任何产品代码，只补强了 `.gitignore`。  
> 审计范围：本机运行时配置、`dist/` 发行包、`build/`、`runtime/`、日志与证据、`cloud/server.js` 与客户端上报、MCP 配置复制功能、`.git` 历史对象。  
> 说明：审计过程中没有打印、复制或外传任何 Key 明文；下文只写字段名、长度和文件位置。

---

## 一、给非技术评委的三五句话结论

**正常使用不会泄露。** 咕嘎的模型 API Key 只存在你电脑的用户目录里（`%LOCALAPPDATA%\GUGA\ai_config.json`），不会上传到咕嘎云端，不会被打进发行 zip，也不会写进日志、证据截图或任务回执；“复制 MCP 配置”复制出来的片段里同样没有 Key。

**但有三件事需要你知道。** 第一，这个文件是明文 JSON，靠 Windows 用户目录权限保护，同一个 Windows 账号下的其他程序理论上都能读，所以不要把电脑借给不可信的人，也不要给不可信的软件开 MCP。第二，工程目录里现在还留着一份带真实 Key 的本地备份（`build/private-config-backup/`）和一份旧 Key 备份（`runtime/`），它们不在 Git、不在发行包，但谁拿到这个目录就能看到，建议今天删掉并作废旧 Key。第三，不要把桌面这枚 Key 填进云端网页的“模型设置”，那会让 Key 离开你的电脑、落到服务器上。

**发行包和仓库是干净的。** 实测发行 zip 的 5133 个条目里没有真实 Key，也没有 `ai_config.json`；`.git` 对象库的 3471 个历史文件里没有命中真实 Key，只有模板占位符。

**如果测试机“没填 Key 却有 Key”，不是包自带。** 对 20261108d 包做了逐字节扫描（含 exe 内嵌归档与 PYZ），0 处命中；代码里唯一能在用户未输入时出现 Key 的路径，是首次启动把安装目录里遗留的 `_internal\ai_config.json` 静默复制到用户目录并回填设置页（详见第七节）。

## 三、逐条审计

### 1. 存储：Key 落在哪、权限如何、升级/换机去哪

**结论：有条件会泄露（本地明文）。“会不会被别的软件读到”取决于 Windows 账号信任边界。**

#### 1.1 落点与优先级

配置文件名是 `ai_config.json`，真实落点由 `core/guga_paths.py` 决定：

| 优先级 | 来源 | 代码 |
| --- | --- | --- |
| 1 | 环境变量 `GUGA_HOME` | `core/guga_paths.py:77-79` |
| 2 | `%LOCALAPPDATA%\GUGA` | `core/guga_paths.py:80-82` |
| 3 | `%APPDATA%\GUGA` | `core/guga_paths.py:83-85` |
| 4 | `%USERPROFILE%\.guga` | `core/guga_paths.py:86-88` |
| 5 | 安装目录（仅前面都不可写时兜底） | `core/guga_paths.py:89`、`:106-113` |

实际写盘前会用一个探针文件确认“真的可写”，不是“目录存在就算”。所以正常安装不会把 Key 写进 `Program Files`；只有前四个位置全不可写时，才会落到安装目录，并且后续写盘会明确失败（`guga_paths.py:106-113`）。

本机实测：真实 Key 位于 `%LOCALAPPDATA%\GUGA\ai_config.json`，只有一个 `api_key` 字段（长度 115）。

#### 1.2 明文与权限

- 写盘是普通 UTF-8 JSON，原子替换（`guga_paths.py:213-238`），**没有加密、没有 DPAPI、没有调用 `icacls` 收权**。
- 写盘会先生成 `ai_config.json.tmp`；进程崩溃时临时文件可能残留，内容同样是明文 Key。`.gitignore` 已排除 `ai_config.json.tmp`。
- 实测 `icacls %LOCALAPPDATA%\GUGA\ai_config.json`：只有 `SYSTEM`、`Administrators` 和当前用户 `l`，且都是继承自用户目录的 `(I)` 项。**其他标准 Windows 用户默认读不到；管理员、SYSTEM、以及任何以当前账号运行的程序能读。**
- 同一文件还保存了云端账号密码（首次配置向导写入 `cloud.password`，`ui/first_run.py:416-430`），也是明文。它不是模型 Key，但泄露后可被用来登录咕嘎云端账号。

#### 1.3 会不会写进安装目录

正常不会。旧的安装目录配置只在“迁移”时被读取：

- 旧路径候选：`core/guga_paths.py:35-58`（打包版是 `_internal/` 和 exe 同目录；源码运行是仓库根/上级）。
- 迁移逻辑：`core/guga_paths.py:157-186`，**只复制、不删除原文件**；用户目录已有配置时不覆盖。
- 结果：如果老版本曾把配置写在安装目录，升级后安装目录里会**继续留一份旧 Key**。安装目录若被共享、打包或发给别人，这一份会跟着走。

#### 1.4 升级、卸载、换机器

- **升级/重装**：配置在 `%LOCALAPPDATA%`，与程序目录分离；代码中没有删除 `ai_config.json` 的逻辑，升级后原样保留。
- **卸载**：仓库里没有卸载清理脚本；删除程序目录不会删除用户目录配置，Key 留在原处。
- **换机器**：Key 不随云端同步。跨设备链路只同步“装了什么软件”的清单，不同步模型配置（见第 4 节）。换机需要重新填写。
- **转卖/借出电脑**：下一个能登录该 Windows 账号的人（或管理员）可以读到这把 Key。建议转手前删除 `%LOCALAPPDATA%\GUGA\ai_config.json`。

**最小改法（未实施，仅建议）**：① 设置页增加“清除本机模型凭据”按钮；② 用 Windows DPAPI（`CryptProtectData`）加密 `api_key` 字段；③ 迁移成功后删除旧文件，或在界面明确提示旧路径；④ 文档写明转卖前清配置。

### 2. 发行包：zip、`dist/`、`build/` 里有没有 Key

**结论：当前公开发行包不会泄露；构建扫描存在方法学盲区，换机器/第三方 Key 可能漏。**

#### 2.1 实测结果

| 对象 | 结果 |
| --- | --- |
| `dist/GUGA-Desktop-win64.zip` | 5133 个条目；逐条目扫描后 **0 处命中当前真实 Key** |
| zip 内 `ai_config*` | 只有 `_internal/ai_config.example.json`，没有 `ai_config.json` |
| zip 内 `.env` / `*.key` / `*.pem` | 无用户配置；只有 Python 依赖自带的 CA 证书 `cacert.pem` |
| `dist/GUGA-Desktop/`（解包目录） | 同样只有 `ai_config.example.json`，无运行期配置 |
| `release-private/`（私有测试包） | 未命中当前真实 Key；其配置来自 `sanitize_config()` 置空后的副本 |
| `build/private-config-backup/ai_config.20261107.bak.json` | **命中当前真实 Key（同一把，出现 1 个字段）** |

`build/private-config-backup/` 不在发行 zip 里，也不在 Git 里（`build/` 已被忽略），但它是**工程目录内的明文备份**，属于本地泄露面。见第四节 P1。

#### 2.2 公开打包流程到底怎么防

`tools/build_guga_exe.py` 的顺序是：

1. 读**仓库根**的 `ai_config.json`，收集真实凭据值（`:367-379`）；
2. 只把 `ai_config.example.json` 模板复制进 `_internal/`（`:401-405`）；
3. 对 `dist/GUGA-Desktop` 做强制扫描，发现 Key 就删除产物并中止（`:410-412`）；
4. 打 zip（`:437-444`），其中说明文档由 `build_manual()` 生成。

扫描器 `tools/release_guard.py` 的覆盖范围：

- 文本后缀集合：`.json .txt .ini .cfg .conf .yaml .yml .env .md .py .ps1 .bat .cmd .toml .xml .html .htm .js .css .csv .log .spec .properties .example`（`:31-35`）；
- 文本文件：既比对“本机配置里的真实值”，也匹配 `sk-`、`LTAI`、`ghp_`、`AIza` 四种形态（`:37-42`、`:141-155`）；
- 二进制文件（exe/dll/pyd/pyz 等）：**只比对真实值，不做形态匹配**（`:29-30`、`:156-157`）；
- 发现后默认删除产物（`:164-183`）。

#### 2.3 盲区（重要，不粉饰）

1. **构建读错了配置文件。** `build_guga_exe.py:369` 读的是仓库根 `ai_config.json`；本机这把真实 Key 实际在 `%LOCALAPPDATA%\GUGA\ai_config.json`。本次构建日志因此打印“本机 ai_config.json 无非空凭据”，`secrets` 为空集。**结果是：二进制文件（exe/PYZ/pyc）那一层“精确值扫描”没有针可扎，等于只做了文本形态扫描。**
2. **二进制不扫形态。** 如果换一台构建机、或有人把另一把 Key 硬编码进代码，exe/PYZ 里既没有 `sk-` 形态扫描，也没有本机真实值可比对，就会漏。
3. **PYZ/pyc 里的常量可能被压缩。** 即使加了 `sk-` 形态，PyInstaller 的 PYZ 是压缩容器，简单按字节搜索看不到里面的字符串常量；需要先解包/反序列化再扫。
4. **zip 本身没有再扫一遍。** `verify_release_zip()`（`build_guga_exe.py:337-352`）只校验结构（主 exe、入口、目录），不校验凭据；`assert_clean()` 只扫打包前的 `OUT`（`:411`）。zip 根目录的两份说明文档由 `build_manual()` 生成，**没有经过凭据扫描**。本次实测文档干净，但流程上是一条漏网路径。
5. **`.jsonl`、`.pyi` 等后缀不在文本集合。** 这些文件只享受“真实值比对”，不享受形态扫描。

**最小改法（未实施，仅建议）**：① 构建时同时读取 `%LOCALAPPDATA%\GUGA\ai_config.json`，或要求通过 `GUGA_BUILD_SECRETS` 显式提供；② `assert_clean()` 增加一条“解包 zip 后整体再扫”；③ 对 PYZ 用 `PyInstaller.archive.readers.CArchiveReader` 解开后再扫字符串常量；④ 把 `.jsonl`、`.pyi`、`.ts` 等加入文本后缀；⑤ 扫描失败时不要打印“无真实 Key”这种超出实际覆盖面的结论。

#### 2.4 `dist/` 里的个人路径

`dist/build-report.json`（`:420-432`）和 `dist/build-integrity.json` 记录了 `D:\rengongzhineng\...`、`C:\Users\l\Desktop\...` 这类本机绝对路径。**没有 Key**，但属于个人信息。它们不在 zip 内；如果直接把整个 `dist/` 目录上传，会带出去。建议发布只传 zip。

### 3. 日志、证据、截图、回执

**结论：当前不会；日志函数无脱敏，属未来风险。**

#### 3.1 日志写入规则

`core/app_log.py`：

- 写到 `%USERPROFILE%\.guga\logs\startup.log`（`:16-22`）；
- 单文件 512 KB 轮转（`:12`、`:30-33`）；
- `detail` 原样截断 4000 字后写入（`:25-41`）；
- 未捕获异常和线程异常整段 traceback 写入（`:44-49`、`:55-70`）；
- **没有任何 Key/Authorization 脱敏**。

当前调用点没有把配置对象、请求头或 Key 传进 `log()`。实测：

- `%LOCALAPPDATA%\GUGA` 全目录扫描：除 `ai_config.json` 本身外，0 处命中真实 Key；
- `%USERPROFILE%\.guga`、`d:\rengongzhineng\.guga`：0 处；
- 仓库 `runtime/`、`build/`、`dist/`：0 处（`build/private-config-backup` 除外，见第 2 节）；
- `tools/clean_bench/` 下上百个测试用 `ai_config.json`（`runs/`、`.cache/installs/`）：0 处命中真实 Key，均为测试夹具；该目录已被 `.gitignore` 整体排除。

#### 3.2 证据与回执

- `build/*evidence.json`、`docs/demo/evidence/*/result.json`：字段是 `prompt`、`answer`、`text`、`status`、`screenshot` 这类业务内容，没有请求头/Key。实测 0 处命中真实 Key。
- `runtime/clean/*` 是测试夹具：其中的 `cloud-hits.jsonl` 会记录测试登录请求体，`cross_home/ai_config.json` 有 13 字符的假 Key 和 5 字符的假密码。**这些是测试假数据，不是真实凭据**，但建议不要把 `runtime/clean/` 一起发给评委。
- 截图：咕嘎只截目标软件窗口做视觉取证，不会自动截“咕嘎设置页”。除非用户自己截图/录屏时把 Key 输入框拍进去，否则截图不含 Key。

**最小改法（未实施，仅建议）**：在 `app_log.log()` 入口加一层脱敏：`Authorization`、`Bearer`、`sk-` 形态、`api_key=`、`password=` 统一替换为 `[REDACTED]`；并给 `log_exc()` 增加异常消息脱敏。

### 4. 云端：Key 会不会传给服务端或跨设备

**结论：桌面端不会上传模型 Key；云端网页“模型设置”是有条件泄露点。**

#### 4.1 桌面端上报了什么

- 登录：只发咕嘎云账号的用户名/密码（`core/butler_cloud.py:253-272`、`cloud/server.js:1085-1100`）。服务端存的是加盐哈希，不存明文密码。
- 派单：只发 `goal / space / device / requiredTools`（`core/butler_cloud.py:300-313`）。没有 `api_key`。
- 设备清单：只发软件名、可启动标识、版本、路径摘要、别名（`core/local_tools.py:321-350`、`cloud/server.js:1506-1525`）。**路径摘要是安装路径，属隐私数据，但不是凭据。**
- 上报请求头用设备配对 token，不是模型 Key（`core/local_tools.py:365-406`）。

结论：**模型 Key 不会因为“派单/跨设备/清单上报”离开本机。**

#### 4.2 云端服务端自己的 Key

`cloud/server.js` 的大模型配置来自环境变量，或云端网页“模型设置”：

- 启动时读 `cloud/data/llm_config.json`，把 `apiKey` 装进内存（`:200-208`）；
- 网页设置接口接收 `apiKey`，测试通过后 `saveLLMCfg()` **明文写回 `data/llm_config.json`**（`:2036-2075`、`:209-211`）；
- 返回前端时只回 `apiKeyMasked`（最后 4 位），不回明文（`:2075`）；
- 日志只打印模型名和 Base URL，不打印 Key（`:206`、`:2074`）。

**风险条件**：如果用户把桌面这枚 Key 粘进云端网页的模型设置，Key 就会：
1. 通过网络发到服务器；
2. 以明文落到 `cloud/data/llm_config.json`；
3. 服务器管理员/拿到该目录的人可读。

如果云端用的是另一把“服务器专用 Key”，则桌面 Key 仍然只在本机。建议：**云端和桌面各用一把 Key，云端那把设置额度上限，绝不共用。**

#### 4.3 服务端日志里的其他凭据

- 未配置 `JUDGE_PASS/TEST_PASS` 时，启动会生成随机临时口令并打印一次（`cloud/server.js:35-44`、`:160-173`）。若 stdout 被 systemd/journal/容器日志收集，口令会进日志。
- `cloud/.env.example:15-17` 写有示例口令 `Guga@2026`；若原样复制成 `.env` 部署，就是“公开的默认口令”。上线前必须改。
- 会话 token 存在 `cloud/data/sessions.json`（`:1098-1099`），属服务端凭据；`cloud/data/` 已被 `.gitignore` 忽略。

**最小改法（未实施，仅建议）**：网页设置页明确写“这里填的是服务器 Key，不要填个人桌面 Key”；启动日志只打印“已生成临时口令，见控制台/首次登录页”，不打印明文；`.env.example` 改成空值并加注释。

### 5. MCP 配置（重点）

**结论：复制出来的片段里没有 Key；粘进 WorkBuddy / 豆包 / JoyCode 不会把 Key 写进它们的配置或日志。但“同账号程序可读配置文件”是操作系统层面的事实，不由 MCP 片段决定。**

#### 5.1 片段里到底有什么

`core/adapters/mcp_channels.py`：

- `_workspace_entry()` 只放两个环境变量：`PYTHONIOENCODING=utf-8`，以及可选的 `GUGA_CLIENT_ID=<软件id>`（`:233-243`）。**故意不写 `GUGA_WORKSPACE`**，避免带出本机绝对路径。
- 文件型条目只有 `command / args / env / disabled`（`:246-256`）。
- 豆包表单条目是 `name / transport=stdio / command / params / env`（`:259-270`）。
- 片段生成前有双重拦截：
  - `has_model_key(text)`：匹配 `sk-` 形态，或匹配本机 `ai_config.json` 里所有 `api_key/token/secret/password` 的真实值（`:273-303`）；
  - 一旦命中，直接 `ok=False` 拒绝显示（通用条目 `:399-402`，豆包表单 `:416-419`，文件型 `:435-438`）。

所以，**“一键复制配置”复制到剪贴板的内容不含 Key**；剪贴板里只有本机 Python/exe 路径和两个非敏感环境变量。即使其他程序读剪贴板，也拿不到 Key。

#### 5.2 粘进第三方软件之后

- WorkBuddy：整段 `mcpServers` JSON 合并进它自己的配置文件，里面没有 Key。
- JoyCode：同样走文件型配置，没有 Key。
- 豆包：表单字段“云端保存，无本地文件”（`:260`），保存的也只有命令/参数/环境变量，没有 Key。
- 第三方软件通过 MCP 调用 `report_app` 时，传给咕嘎的是软件名、exe 绝对路径、版本、能力；咕嘎写进 `app_reports.json`。这些不是凭据（`core/adapters/guga_mcp_server.py:171-177`）。
- MCP Server 自身不导入咕嘎引擎，也不读 `ai_config.json`（`guga_mcp_server.py:1-19`、`:38-43`）；它只依赖标准库、MCP SDK 和 `app_reports`。

#### 5.3 仍然要说明的边界

1. 用户目录的 `CONFIG` **不存在**才进入迁移；

## 八、授权模型与云端 Key 边界（产品口径）

### 8.1 口径

授权分两层，必须互相隔离：

- **买软件**：本地功能；模型 Key 由用户自己在本机填写，用用户自己的额度。
- **买账号**：云端服务；才允许服务端使用运营方 Key，按账号权益计费。

由此推出四条硬规则：

1. 本机绝不允许从服务端拿到、缓存或使用运营方 Key；任何“服务器 `llm_config.json`/账号级模型配置 → 本地 `ai_config.json`”的路径都判为缺陷。
2. 无本地 Key 时，本地 AI 功能必须明确不可用，不得静默借用云端额度；云端能力单独鉴权，无权益返回 `CLOUD_NOT_ENTITLED`，界面提示“需购买云端服务”。
3. 设置页必须显示当前 Key 来源：`本机填写 / 从旧配置继承 / 云端下发`；后两者在改造后应消失；显示时打码服务商与后四位。
4. 云端代理调用必须只服务已购账号、服务端记量、本地不落 Key。

### 8.2 “云端 Key 下发到本地”结论：不存在

| 路径 | 代码 | 是否把 Key 送到本地 | 结论 |
| --- | --- | --- | --- |
| 登录 | `cloud/server.js:1084-1100`、`butler_cloud.py:265-276` | 否，只回 token/username | 不会 |
| 派单 | `butler_cloud.py:290-319`、`server.js:1315-1332` | 否，payload 只有 goal/space/executor/device | 不会 |
| 状态轮询 | `butler_cloud.py:351` | 否 | 不会 |
| 设备清单 | `butler_cloud.py:332`、`server.js:1664-1694` | 否，只有软件名/路径/版本 | 不会 |
| 网页模型设置 | `server.js:2026-2076` | 桌面端不调用；GET 只回打码值 | 不会下发到本地 |

**因此，“本地设置里出现运营方 Key”不存在代码路径；实测来源是 7.3 的旧配置继承。**

### 8.3 但云端 Key 仍有三条被越权使用的路径（这才是要修的缺陷）

| 级别 | 路径 | 证据 | 后果 |
| --- | --- | --- | --- |
| **P0** | `POST /api/llm` 只验登录，不验管理员；`apiKey` 留空时沿用运营方 Key，`baseUrl` 可填任意公网地址 | `cloud/server.js:2033-2076`（`:2036` 留空沿用、`:2042-2048` 只挡内网、`:2058-2060` 带 Bearer 发请求、`:2073` 保存） | 任何已登录账号都能把运营方 Key 发到自己控制的公网地址，测试返回 200 后还会持久化。**这是 Key 外泄路径，不是文案问题。** |
| **P0** | `POST /api/tasks`、`POST /api/chat` 只验登录，没有云端权益校验 | `cloud/server.js:1315`、`:2315`；`users.json` 只有 `username/salt/hash`（`:158-168`） | 只买软件的账号登录后即可用运营方 Key 跑云端任务；无 `CLOUD_NOT_ENTITLED`、无按账号计量。 |
| **P2** | `GET /api/llm` 任何登录账号可读模型名、Base URL、Key 后四位 | `cloud/server.js:2026-2031` | 信息面暴露；应仅管理员可见。 |

### 8.4 最小改法（按层，未实施）

**服务端（`cloud/server.js`）**

1. `users.json` 增加 `cloudEntitled`（布尔）与 `cloudQuota`（次数/Token）；初始化账号时默认 `false`。
2. 新增中间件 `requireCloud`，挂在 `POST /api/tasks`、`POST /api/chat`；无权益返回 `403 {code:'CLOUD_NOT_ENTITLED', message:'需购买云端服务'}`。
3. `/api/llm` GET/POST 改为仅管理员（`JUDGE_USER` 或显式 `role:'admin'`）；`POST` 在 `baseUrl` 变化时**禁止**沿用旧 Key，必须显式提交；保留 SSRF 防护。
4. 记录按账号计量：每次 `llmJSON` 成功调用累加 `{user, model, promptTokens, completionTokens, at}` 到 `usage.json`；超配额返回 `CLOUD_QUOTA_EXCEEDED`。
5. 运营方 Key 永不返回前端；日志只记录模型名与用户，不记录 Key。

**桌面端（`core/butler_cloud.py` + `ui/`）**

6. 不新增任何“拉取云端模型配置”的调用；桌面永不读写 `/api/llm`。
7. `dispatch`/`chat` 处理 `CLOUD_NOT_ENTITLED` 与 `CLOUD_QUOTA_EXCEEDED`，界面明确提示“需购买云端服务/额度已用完”，不回退到任何本地或服务端 Key。
8. 无本地 Key 时，本地 AI 入口显示“本机 Key 未配置，本地 AI 功能不可用”，不自动改走云端。

**配置与界面**

9. 设置页增加“Key 来源”与打码显示（服务商 host + 后四位）；首次启动遇到旧配置必须显式询问（见 7.7）。
10. 迁移改造为“确认后沿用”，并在确认框中打码展示来源与后四位。

**构建与发布**

11. `assert_clean()` 增加文件名级红线：包内任何非示例 `ai_config*.json` 直接失败；zip 解包后复扫。
12. 发布前用 `--paths-probe-json` + `--selfcheck-json` 在干净 `GUGA_HOME` 下跑一次，断言“无 ai_config.json、无 Key”。

### 8.5 验收判据

- 干净机器解压 d 包启动：`%LOCALAPPDATA%\GUGA\ai_config.json` 不存在，设置页 Key 为空；
- 只买软件账号：`POST /api/tasks` 返回 `CLOUD_NOT_ENTITLED`，界面提示购买；本地无 Key 时本地 AI 明确不可用；
- 已购云端账号：云端任务可跑，`usage.json` 有该账号计量；本地 `ai_config.json` 始终无运营方 Key；
- 任何账号调用 `GET/POST /api/llm` 均被拒（管理员除外）；`POST` 不能把运营方 Key 发往新 `baseUrl`；
- 设置页能看到 `本机填写` 来源；旧配置继承场景必须先弹确认框。
