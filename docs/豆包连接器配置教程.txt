咕嘎 · 豆包自定义连接器配置教程
（按豆包官方帮助中心 2026-11-06 版口径；g 版起 HTTP 优先）

这份教程只讲豆包。豆包的 MCP 入口是「插件·技能·伙伴 → 插件 →
右上角 + 添加 → 新建自定义连接器」，不是“连接器市场”，
也不要照搬 WorkBuddy 的配置文件说法。

一、先弄清楚三件事
----------------------------------------------------------------
1. 发现：豆包连上咕嘎的 MCP 后，调用一次 report_app 自报自己的 exe 路径，
   咕嘎记住，以后直接启动，不用再猜安装目录。
2. 指挥：派单仍然是把豆包窗口置前、模拟键鼠、读回结果；
   MCP 只做发现，不会把派单改成接口调用。
3. 豆包没有本地 mcpServers 配置文件，只能登录后在官方界面新建，
   配置保存在云端。因此咕嘎无法自动写入，也不把“已创建条目”说成“已接入”。

咕嘎里的状态只按三态显示：
   已检测到配置 / 界面已显示 guga / 未验证
只有真实握手通过才显示“已连接”；l 版起再细分为：
   · 未验证：需在官方界面添加
   · 通道已就绪，等待豆包首次握手
     （咕嘎端点自检通过、5 个工具齐全，但还没收到豆包的 initialize）
   · 曾连接过，当前未验证
     （以前真实握手成功过，但咕嘎 HTTP 端点重启了或那次连接进程已退出）
   · 已连接（真实握手）
     （以豆包客户端 clientInfo 的 initialize 为准，不是“界面里看到条目”）
豆包是 HTTP 连接器，没有本地配置文件，所以状态判定不看 mcpServers 文件。
20261110l 起，接入面板与启动自检的「外部软件」项读同一份真实握手证据
（<workspace>\.guga\mcp-connections\doubao.json 与 mcp_http.json 的 client 字段）：
只要豆包真的 initialize 过，自检就不会再把豆包列进“未发现”，也不会出现
“面板已连接、自检说未接入”的分叉。自检仍不启动第三方界面，所以该项本身标“未测”。

二、咕嘎这一侧：本机 HTTP 端点（HTTP 优先）
----------------------------------------------------------------
g 版起咕嘎主程序启动时会自动在本机开一个 MCP HTTP 端点：
· 只绑 127.0.0.1，绝不绑 0.0.0.0；
· 路径固定 /mcp，端口从 18760 起，被占用就 +1，直到找到空闲端口；
· 实际端口写在 %LOCALAPPDATA%\GUGA\runtime\mcp_http.json，
  接入面板豆包卡片上的「服务器 URL」读的就是这个真实端口；
· 工具集与 STDIO 完全一致（5 个：report_app / get_task /
  report_progress / submit_artifact / ask_guga）。

单独排查端点（不开桌宠）：
   GUGA-Desktop.exe --guga-mcp-http
然后看 runtime\mcp_http.json 里的 state 与 port。
关掉端点：在 ai_config.json 里写 "mcp_http_enabled": false，或设
环境变量 GUGA_MCP_HTTP=0，再重启咕嘎。
WorkBuddy / JoyCode 继续用 STDIO（--guga-mcp），不受影响。

三、官方入口（按这个走，别找“连接器市场”）
----------------------------------------------------------------
1. 登录豆包，并确认账号有个人订阅或团队/企业额度
   （官方门槛：没有额度进不了豆包工作）。
2. 打开「插件·技能·伙伴」→「插件」。
3. 点右上角「+ 添加」→「新建自定义连接器」。
4. 官方传输类型只有 HTTP / STDIO，没有 SSE。

四、按表单填写（首选 HTTP）
----------------------------------------------------------------
咕嘎接入面板的豆包卡片上有「复制连接器字段」：复制出来的是
“字段：值”的纯文本（不是 JSON），逐栏照抄。

首选（HTTP）：
· 服务器名称：guga
· 传输类型：HTTP
· 服务器 URL：http://127.0.0.1:<实际端口>/mcp
  （卡片上写的是真实端口，例如 http://127.0.0.1:18760/mcp；
    端口被占用时会变成 18761、18762……照卡片抄即可）
· Headers：留空，不要填任何 Key
· 点「保存」。官方未要求重启。

备选（STDIO，HTTP 端点未启动或端口冲突时用）：
· 传输类型：STDIO
· 运行命令：你解压出来的 GUGA-Desktop.exe 完整路径，例如
    D:\GUGA\GUGA-Desktop\GUGA-Desktop.exe
  不要填 Python 解释器或脚本路径，也不要填任何开发目录。
· 参数：--guga-mcp
· 环境变量：PYTHONIOENCODING=utf-8（表单有这一栏才填，没有就跳过）

重要限制（官方原文）：
· 这个自定义连接器只在豆包「工作」模式生效；
  对话模式调不到，任务输入框里用 / 和 @ 也搜不到 guga。
  豆包弹窗原文：「自定义连接器仅支持在本地电脑中使用」。
· 所以请进入「工作」模式后的任务里使用。

五、怎么判断“接上了”
----------------------------------------------------------------
官方没有独立的“连通状态 / 工具清单”页面，只能在「插件 → 管理」里
看到条目。因此：
1. 「插件 → 管理」里出现 guga 条目 = 界面已显示 guga（仍不算接入成功）。
2. 打开咕嘎的接入面板，点豆包这一行的「验证连接」：
   HTTP 条目会真实连一次 http://127.0.0.1:<端口>/mcp，
   做 initialize + list_tools + get_task，并列出 5 个工具；
   STDIO 条目会真实拉起 GUGA-Desktop.exe --guga-mcp。
   成功显示“已连接（真实握手 / 5 个工具）”；
   · 如果只有咕嘎自检通过、豆包还没发起调用，会如实显示
     “通道已就绪，等待豆包首次握手”，不会冒充“已连接”；
   失败写原因：端点没启动 / 端口冲突 / exe 不存在 / 超时 / 工具清单不符。
3. 未做第 2 步之前，一律标“未验证”，不要写“已接入”。

六、连接成功后
----------------------------------------------------------------
1. 让豆包调用一次 report_app，参数填：软件标识 doubao、名称、
   exe 绝对路径、版本、能力。
2. 咕嘎把路径写进 %LOCALAPPDATA%\GUGA\app_reports.json，下次启动直接用。
3. 豆包升级或换安装目录后，再调用一次 report_app 覆盖旧记录即可。

七、OCR 与豆包派单的关系
----------------------------------------------------------------
豆包界面文字主要靠截屏 + 系统 OCR 读。OCR 不可用时咕嘎会降级：
· 先用 UIA（ValuePattern / TextPattern）读界面文本；
· 再用剪贴板回读核对输入；
· 仍读不到才用 OCR 兜底。
OCR 不可用不会中断复合任务：回执和证据会标注 ocr_unavailable，
失败码也是 ocr_unavailable，不会出现 adapter_exception 这种无信息文案。

缺中文 OCR 语言包的装法：
  设置 → 应用 → 可选功能 → 添加功能 → 搜索并安装
  “中文(简体) 光学字符识别”，装完重启咕嘎（不用重启电脑）。
装好后在启动自检里点 OCR 这一项的「重试」，应显示“字符重合率 ≥90%”。

八、常见问题
----------------------------------------------------------------
问：找不到「新建自定义连接器」？
答：入口是「插件·技能·伙伴 → 插件 → 右上角 + 添加」；
     不是“连接器市场”。版本太旧就先升级豆包。

问：HTTP 和 STDIO 选哪个？
答：首选 HTTP（本机直连，保存即通）；端点没启动或端口冲突时再选 STDIO。

问：URL 里的端口为什么不是 18760？
答：18760 被别的程序占用时咕嘎会自动 +1，实际端口写在接入面板和
     runtime\mcp_http.json 里，照面板上的 URL 抄即可。

问：保存后为什么没有“工具列表”？
答：官方没有独立的连通状态/工具清单页面，只能看「插件 → 管理」；
     是否真的连上以咕嘎「验证连接」的真实握手为准。

问：为什么在对话模式里调不到 guga？
答：自定义连接器只在豆包「工作」模式生效；对话模式和 /、@ 都搜不到。

问：咕嘎提示 adapter_exception？
答：这个码仍可能出现，表示「本机输入通道」这一步失败，连接器配置本身通常没问题。
     旧版（q 及更早）有一个已知原因：启动自检给 SendInput 设了全局类型签名，之后派单按键会报
     ArgumentError: argument 2: TypeError: expected LP_INPUT instance instead of pointer to _INPUT，
     界面显示「第 1/2 步（豆包）失败：… 缺什么：adapter_exception」，重启不能绕过。
     20261110r 起自检与派单各自绑定签名，已修掉这条；仍看到就先右键「导出诊断」发回。

问：咕嘎提示 KeyError: 2？
答：这是 20261110r 及更早的缺陷：UIA 返回的输入框坐标是字典
     {"left":…,"top":…,"right":…,"bottom":…}，旧代码按列表下标取 rect[2]。
     20261110s 起同时兼容字典 / 列表 / 元组，无效坐标按原逻辑跳过。
     不需要改豆包设置，已保存的连接器配置也不受影响。

问：失败原因写「缺什么：ocr_empty」？
答：表示 OCR 引擎本身可用，但这次对豆包窗口识别到 0 行 0 字（不是适配器异常）。
     在豆包窗口按 Ctrl+R 刷出对话页并保持可见后重派；仍为空到「设置 → 自检」
     重跑“系统 OCR”，并右键「导出诊断」把 zip 发给开发者。

问：配置里会有我的模型 API Key 吗？
答：不会。咕嘎复制出来的配置只有本地 URL / 命令和参数；
     模型 Key 只由你在咕嘎首次配置里自己填，不随包分发，也不会写进这里。

问：模型报 401/403，和豆包连接器有关吗？
答：无关。模型请求打在你配置的 base_url 上，凭据是本机 Key；豆包连接器只负责
     “指挥豆包”这一条链路。先右键桌宠 →「⚙️ 模型设置」→「验证 Key（直连/系统代理）」
     复验；失败文案会写清是 Key 无效、没有模型权限，还是额度不足。
     Key 读写时会自动去 BOM/零宽字符和首尾空白；中间夹空格/换行会拒绝发送。
     失败文案还会带“长度 + 前四 + 后四 + 来源”，方便和之前能通的配置对比。

问：云端账号入口在哪？没买云端会影响豆包吗？
答：右键桌宠 →「☁ 云端账号（可选）…」，填服务地址/账号/密码后可先「测试登录」。
     不填不影响本地对话、打开软件、截图分析和豆包派单，只影响云端派单/跨设备。
