# 咕嘎如何识别用户电脑上的适配软件

> 面向作品介绍、评审答疑与答辩。  
> 前半部分写给非技术评委，后半部分是按真实代码逐行梳理的技术细节。  
> 代码基线：2026-11-08。文中所有行号均指当前仓库文件；若后续代码变动，以代码为准。  
> **重要**：第 9 节是"发现靠 MCP 自报、指挥靠界面自动化"的目标口径与实现状态。当前产品里有三条并行的识别路径，第 10 节如实列出它们与声明清单之间的不一致，不做美化。

## 一、先说人话：咕嘎怎么"认出"你电脑上的 AI

可以把咕嘎理解成一个刚入职的管家。它要指挥你电脑上的豆包、WorkBuddy、JoyCode 干活，第一步不是点按钮，而是**先找到这些软件装在哪、有没有真的能干活**。

它找软件的方式，像人找一家店：

1. **你告诉它在哪**——你在设置里手动指定过路径，它直接记下来（最优先）。
2. **店自己递名片**——软件连上咕嘎的 MCP 服务时，主动报一句"我叫什么、我的 exe 在哪、我是什么版本、我会干什么"。咕嘎把这张名片存进本机档案，下次直接用。
3. **按地址找**——如果没人告诉、也没人递名片，咕嘎就按声明清单去查：先看常见安装目录，再查 Windows 注册表、开始菜单快捷方式、系统 PATH、正在运行的进程，最后才扫绿色版目录。
4. **找到之后还要"验工位"**——exe 存在不等于能用。咕嘎会看窗口有没有起来、是不是登录页、是不是白屏、是不是停在上一次的编辑页。只有真正能输入，才算"可派单"。

关键是：**找不到就说找不到，找到但不可用就说为什么不可用**。它不会因为找不到豆包，就让云端模型"假装豆包"写一份答案交差。

### 一句话结论

| 问题 | 答案 |
| --- | --- |
| 咕嘎靠什么找软件？ | 用户指定 > MCP 自报路径 > 声明清单 + 注册表/开始菜单/常见目录/PATH/进程探测兜底 |
| 找到 exe 就一定能用吗？ | 不一定。还要过"窗口、登录、白屏、编辑页"四道检查 |
| 识别结果存在哪？ | `%LOCALAPPDATA%\GUGA\app_reports.json`（MCP 自报）、`runtime\app_registry.json`（探测缓存）、`runtime\local_tools.json`（本机工具清单缓存） |
| 换一台电脑还认得出吗？ | 认得出"这类软件"，但具体路径必须重新探测或让软件重新自报；咕嘎不把某台机器的路径写死 |
| 跨设备派单怎么知道对方装没装？ | 各设备把工具清单上报云端；派单时用 `requiredTools` 核对，缺工具直接拒绝并说明缺什么 |

## 二、识别优先级：目标口径

这是产品对外的统一口径，也是评审最常问的一点：

```
① 用户手动指定
       ↓ 未命中
② MCP 自报路径（report_app）
       ↓ 未命中 / 路径失效
③ 声明清单 + 注册表 / 开始菜单 / 常见目录 / PATH / 运行进程 / 绿色版扫描
```

三条边界必须同时讲清楚：

- **MCP 只负责"发现"**：软件连上来，报一次自己的 exe 绝对路径、版本、能力；咕嘎落盘。
- **MCP 不负责"指挥"**：不通过 MCP 下发任务、不通过 MCP 收答案。派活仍旧是把目标窗口置前、模拟键鼠、读剪贴板/工作区回执。
- **自报路径失效要回退**：文件被删、升级换了目录、记录指向的不是 `.exe`，都只记一条原因并继续按第 ③ 类探测，不能因为一条脏记录让软件再也起不来。

> 实现状态：第 ② 级已经落在 `core/adapters/app_registry.py` 的探测链里（`source=mcp_report`），但豆包/WorkBuddy/JoyCode 三个适配器目前仍各自扫路径，尚未全部消费自报记录。第 9 节单独说明，文末第 10 节列为不一致项。

## 三、声明式清单：一个软件一份 JSON

声明文件在 `core/adapters/apps/`，当前仓库有 3 份正式声明：

- `doubao.json`（豆包）
- `workbuddy.json`（WorkBuddy）
- `joycode.json`（JoyCode）
- `_template.json` 是模板，加载时跳过 `_` 开头的文件（`core/adapters/app_registry.py:169-184`）。

加载顺序（`app_registry.py:138-166`）：`GUGA_APP_ADAPTERS` 环境变量指定目录 → 源码/打包目录 → 用户可写目录 `%LOCALAPPDATA%\GUGA\app_adapters`；同名文件先到先得。  
每个声明会与默认值做深合并（`app_registry.py:302-341`），缺少的字段用默认值补，声明里写错的关键字段会在加载时被 `validate()` 判为无效并记录，而不是静默跳过（`app_registry.py:224-300`）。

### 3.1 顶层字段

| 字段 | 声明里的用途 | 谁真正读它 | 真实状态 |
| --- | --- | --- | --- |
| `schema` | 声明版本，必须是 `guga.app_adapter/1` | `validate()` | 只做校验；不参与运行 |
| `id` | 软件唯一标识，也是覆盖记录、缓存、路由的键 | `app_registry`、`dispatch.adapter_for` | 使用 |
| `name` | 显示名，用于提示、跨设备点名匹配 | `app_registry` 结果、`comp_window._cross_required_tools` | 使用 |
| `aliases` | 别名，用于"豆包/DB"这类口语点名 | 跨设备点名扫描、开始菜单默认别名、窗口名兜底 | 使用（但只在声明驱动的链路） |
| `capabilities` | 能力标签，如 `chat/image/document/research` | `app_registry` 结果里原样返回 | **只展示/诊断，不参与派单路由**；路由读的是 `core/local_tools.py` 的硬编码能力表 |
| `automation` | 自动化方式，如 `ui_only` | `app_registry` 结果里原样返回 | 只展示；适配器选择看 `adapter` 字段 |
| `adapter` | 适配器模块入口，如 `core.adapters.doubao_adapter` | `core/adapters/dispatch.py:42-89` | 使用；加载失败会明确返回 `no_adapter`，不降级成模型代写 |
| `notes` | 人看的备注 | 无 | **纯文档字段，代码不读** |
| `process_names` | 进程名，用于反查 exe、识别窗口 | `app_registry` 探测、豆包适配器 | 使用；WorkBuddy/JoyCode 适配器自己硬编码进程名，不读声明 |

### 3.2 `install`：怎么找安装位置

| 字段 | 声明里的用途 | 代码行为 | 真实状态 |
| --- | --- | --- | --- |
| `user_override` | 是否允许用户手动指定路径 | 为真时读 `runtime/app_registry_user.json`（或 `GUGA_APP_REGISTRY_USER` 指定文件），第一优先级 | 使用 |
| `env` | 环境变量名列表 | 逐个展开，值可以是 exe 或启动器目录 | 使用（第 2 级，在 MCP 自报之后） |
| `common_paths` | 常见安装路径列表，支持 `%LOCALAPPDATA%` 等 | 逐条展开、存在性检查，第一个命中即停 | 使用 |
| `registry.uninstall` | 注册表卸载项匹配规则 | 遍历 HKCU/HKLM 的 64/32 位视图，按 DisplayName 匹配；从 `InstallLocation/InstallDir/InstallPath/DisplayIcon` 取路径；`DisplayIcon` 末尾的 `,0` 会被清理 | 使用（`app_registry.py:624-737`） |
| `registry.app_paths` | 注册表 App Paths 匹配规则 | 遍历 HKCU/HKLM 的 64/32 位视图，读默认值、`Path`、`Executable` | 使用 |
| `registry.location_values` | 从卸载项里读哪些值 | 默认 `InstallLocation/InstallDir/InstallPath/DisplayIcon` | 使用 |
| `start_menu.aliases` | 开始菜单/桌面快捷方式名 | 不写时默认用 `id/name/aliases`；匹配 `.lnk` 文件名，再解析快捷方式目标 | 使用（`app_registry.py:738-880`） |
| `start_menu.roots` | 额外的快捷方式目录 | 默认查用户开始菜单、公共开始菜单、桌面 | 使用 |
| `portable.roots` | 绿色版扫描根目录 | 只在常规来源全没命中时才扫；跳过 Windows/缓存/AppData 等目录 | 使用（`app_registry.py:881-947`） |
| `portable.name_globs` | 绿色版 exe 文件名通配 | 与声明 `id`/`name` 再核对一次，避免扫到同名无关程序 | 使用 |
| `portable.depth` | 扫描目录深度 | 默认 2 层 | 使用 |
| `portable.budget_ms` | 扫描时间预算 | 默认 1200 ms，超预算立即停 | 使用 |
| `portable.max_entries` | 最多遍历条目数 | 默认 600 | 使用 |
| `path_lookup` | 是否查系统 PATH | `shutil.which(exe_name)` | 使用 |
| `detect_running` | 是否先扫运行中的进程 | 为真时先枚举进程，按进程名反查 exe；命中则记 `running_process` 来源 | 使用；注意**成本前置**：进程枚举在探测开始时做，但排序仍在第 7 位 |
| `install.single_instance`（豆包适配器自创） | 声明里被当作单实例 exe 提示 | 豆包适配器读的是 `install.single_instance`，而默认值把它定义在 `launch.single_instance` | **字段位置不一致，实际永远读不到**（见第 10 节） |

## 四、六种探测手段：各自用在哪、什么顺序

先明确一件事：**"找 exe"和"认窗口"是两套信号。** 文件路径、注册表、开始菜单、PATH、进程用于找 exe；窗口标题/类名/尺寸用于确认"这个窗口是不是它、能不能输入"。环境变量既可用于找 exe，也可用于指定工作区。

### 4.1 声明驱动链（`app_registry.probe`）的完整顺序

`core/adapters/app_registry.py:1118-1280` 的探测顺序如下，命中即停：

| 顺序 | 来源 | 代码位置 | 具体做法 | 失败语义 |
| --- | --- | --- | --- | --- |
| ① | 用户手动指定 `user_override` | `app_registry.py:1144-1155` | 读 `runtime/app_registry_user.json`（或 `GUGA_APP_REGISTRY_USER`），支持弹窗写入 | 文件不存在/路径无效 → 继续下一级 |
| ② | MCP 自报 `mcp_report` | `app_registry.py:1156-1170` | 读 `app_reports.json`，校验绝对路径、`.exe`、文件存在且非空；失效时写 `mcp_report_invalid` 原因并回退 | 脏记录只记录不阻断 |
| ③ | 环境变量 `env` | `app_registry.py:1172-1187` | 逐个展开环境变量；值可以是 exe 或启动器目录 | 空值/不存在 → 继续 |
| ④ | 常见安装路径 `common_paths` | `app_registry.py:1189-1199` | 展开 `%VAR%`，逐条 `is_file()` | 全部不存在 → 继续 |
| ⑤ | 注册表卸载项 `registry.uninstall` | `app_registry.py:1201-1203` → `624-737` | HKCU/HKLM × 64/32 视图，按 DisplayName 匹配，读取安装位置值 | 无匹配 → 继续；**Access Denied 记 error，不判"未安装"** |
| ⑥ | 注册表 App Paths | 同上 | HKCU/HKLM × 64/32，读默认值/Path/Executable | 无匹配 → 继续 |
| ⑦ | 开始菜单/桌面快捷方式 | `app_registry.py:1205-1207` → `738-880` | 用户/公共开始菜单 + 桌面，按别名匹配 `.lnk`，解析快捷方式目标 | 无匹配 → 继续 |
| ⑧ | 系统 PATH | `app_registry.py:1209-1213` | `shutil.which(exe_name)` | 未找到 → 继续 |
| ⑨ | 运行中的进程 | `app_registry.py:1215-1219` → `948-977` | 按 `process_names` 匹配进程，反查 exe 路径；排除 CrashHandler 等附属进程 | 未运行 → 继续 |
| ⑩ | 绿色版/自定义目录 | `app_registry.py:1221-1225` → `881-947` | 只在前面全没命中时扫描；受 `budget_ms/max_entries/depth` 限制 | 超预算/超条目 → 记 unknown，不硬撑 |

> 细节：`detect_running` 为真时，进程枚举在探测开始时就会做一次（为了给后续来源提供 `running` 信息），所以**第一次探测的耗时里包含一次全进程快照**；但它在优先级排序里仍是第 ⑨ 位。

### 4.2 每种手段的回答边界

| 手段 | 能回答什么 | 不能回答什么 |
| --- | --- | --- |
| 文件路径 / 常见目录 | "这个默认位置有没有 exe" | 装在非默认盘、改了目录、绿色版 |
| 注册表 | "安装程序登记过没有" | 绿色版、无安装器、部分国产软件根本不写卸载项 |
| 开始菜单/桌面 | "用户是从哪个快捷方式启动的" | 快捷方式被删、目标被移动、只从 exe 直接启动 |
| PATH | "命令行能不能直接调起" | 绝大多数 GUI 软件不进 PATH |
| 进程 | "它现在是不是开着、exe 真实在哪" | 没开的时候无法反查；同名进程会误判（需排除 CrashHandler 等） |
| 窗口标题/类名 | "眼前这个窗口是不是目标软件、够不够大" | 不能反推安装路径；托盘隐藏/最小化时枚举不到 |
| 环境变量 | "用户/企业是否显式指定了路径或工作区" | 普通用户通常不会设 |

### 4.3 三条真实存在的识别链（必须分开看）

产品里不是只有一套识别逻辑。当前实际有：

| 链路 | 用途 | 实际使用的手段 | 是否读声明 | 是否读 MCP 自报 |
| --- | --- | --- | --- | --- |
| `app_registry.probe()` | 声明驱动的完整探测；`mcp_channels.channel_status()` 用它判断接入状态；验证脚本也用它 | 用户指定 → MCP 自报 → 环境变量 → 常见目录 → 注册表 → App Paths → 开始菜单 → PATH → 进程 → 绿色版 | 是 | 是 |
| `local_tools.scan()/inventory()` | 本机"有哪些工具"、派单路由、云端能力清单 | 硬编码 `exe_globs` + 开始菜单快捷方式 + `shutil.which`；**没有注册表、没有 MCP 自报**（`core/local_tools.py:122-128`） | **否** | **否** |
| 适配器/执行器各自扫描 | 真正拉起并操作软件 | 豆包：环境变量 + 常见目录；WorkBuddy：一个 `LOCALAPPDATA` 路径；JoyCode：环境变量 + 注册表 + 开始菜单；`guga_executor`：内置 profile → 进程 → App Paths → 开始菜单 | 豆包读一部分；WorkBuddy/JoyCode/执行器不读 | **均未读** |

这解释了为什么"声明里写得很全，实际换台机器仍可能找不到"：**声明驱动的探测链很完整，但日常派单/清单上报走的是 `local_tools` 和各自适配器，它们并不消费声明。** 第 10 节列出具体证据。

### 4.4 窗口标题/类名怎么用

- `app_registry.launch()` 在拉起后按 `ready.window.title_keywords`、进程名、窗口类名三者之一确认窗口出现，并用 `min_width/min_height` 过滤托盘提示窗（`app_registry.py:978-1045`）。
- `agent/guga_executor.py:178-195` 的 `_win_ok()` 用标题关键词 + 尺寸下限 + 排除托盘/输入法噪声窗口，作为"这是目标软件窗口"的判据。
- 这一类信号**只用于确认窗口身份和可操作性**，不用于推断安装路径。

## 五、缓存与耗时

### 5.1 两层缓存

| 缓存 | 位置 | 存什么 | 谁写 |
| --- | --- | --- | --- |
| 声明/探测缓存 | `%LOCALAPPDATA%\GUGA\runtime\app_registry.json` | 每个 app 的 `status/exe/source/elapsed_ms/attempts` 等 | `app_registry.probe()`（`app_registry.py:415-470`） |
| 本机工具清单缓存 | `%LOCALAPPDATA%\GUGA\runtime\local_tools.json` | `local_tools.scan()` 的结果（含 exe、启动核验、版本等） | `local_tools.scan()`（`core/local_tools.py:227-251`） |
| MCP 自报档案 | `%LOCALAPPDATA%\GUGA\app_reports.json` | 软件自报的 `name/exe_path/version/capabilities/client_id/pid/updated_at` | `report_app` → `core/adapters/app_reports.py` |

### 5.2 缓存失效条件

`app_registry`：

- **声明文件增删改**：`_signature()` 把每个声明文件的 `size + mtime_ns` 和 `app_reports.json` 的 `size + mtime_ns` 做指纹，指纹一变，整份缓存作废（`app_registry.py:194-213`）。
- **`ready` 记录**：不做时间过期，但每次命中都重新确认 exe 还存在；文件被删就重新探测（`app_registry.py:481-490`）。
- **`not_installed`**：默认 600 秒后重试（`DEFAULT_CACHE_TTL_MISS`，`app_registry.py:48-50`）。
- **`unknown`**：默认 120 秒后重试（`DEFAULT_CACHE_TTL_UNKNOWN`）。
- **手动失效**：`invalidate()`、`set_override()` 会主动清缓存。
- 注意：缓存会**先读内存**，再读磁盘文件；`cached=True` 时返回的 `elapsed_ms` 是本次缓存读取耗时，不是首次探测耗时。

`local_tools`：

- 只在"工具集签名"变化时重扫；签名只看 `id/capabilities/automation`，**不看 `exe_globs`、开始菜单名、路径规则**。也就是说，改了安装路径规则不会让旧缓存自动失效（`core/local_tools.py:220-225`、`227-252`）。
- 没有 TTL，缓存文件在就一直用；需要重扫只能删 `runtime\local_tools.json` 或调用 `scan()`。
- `inventory_items()` 默认 `launch_probe=False`，**不启动软件**，只确认 exe 存在（`core/local_tools.py:321-345`）。

### 5.3 实测耗时（2026-11-08，作者机）

用只读脚本 `scripts/verify_app_registry.py --json` 与 `local_tools` 直接计时：

| 场景 | 实测 |
| --- | --- |
| 冷探测第一个声明（豆包，含首次全进程枚举） | 约 **1 秒**（本次 985 毫秒） |
| 同进程内第二个声明（WorkBuddy） | 约 **15 毫秒** |
| 同进程内第三个声明（JoyCode） | 约 **16 毫秒** |
| 模拟"用户指定路径"命中 | **0.0 毫秒**（用户指定排在第一级，直接 stat 命中） |
| 模拟"注册表被拒绝" | 约 **15 毫秒**；状态记为 `unknown`，不假装"未安装" |
| 模拟"未安装" | 约 **0 毫秒**（各来源快速失败） |
| 模拟"绿色版目录"命中 | 约 **15 毫秒** |
| 热探测命中（缓存里已有记录） | **0.0 毫秒**（源码回传 `cached=True, elapsed_ms=0`） |
| `local_tools` 冷扫描（含开始菜单 PowerShell 解析） | 约 **1.56 秒** |
| `local_tools` 热读取缓存 | 约 **0.3 毫秒** |

结论：**首次启动的秒级开销主要来自一次全进程快照和开始菜单快捷方式解析；之后是毫秒级。** 这也是为什么探测结果必须落盘缓存，而不是每次派单都重扫。

## 六、能力表 → 云端 inventory → 跨设备 `requiredTools`

这一条解决的是"我在 A 电脑派活，B 电脑装没装这个软件？"

### 6.1 本机能力表

`core/local_tools.py:36-81` 里有一张**硬编码**的 `APPS` 能力表：

- 豆包：`chat/writing/image/document/research`
- WorkBuddy：`document/slides/agent`
- JoyCode：`coding/website/agent`
- 元宝、智谱、Trae CN、Kimi 等也在表里（部分没有对应声明，见第 10 节）

每条包含 `id/name/exe_globs/capabilities/automation/adapter/summary`。

### 6.2 本机可用工具

`local_tools.scan()` 对每条能力表做：

1. 展开 `exe_globs` 找 exe；
2. 开始菜单/桌面快捷方式解析；
3. `shutil.which` 兜底；
4. 可选真启动核验（`launch_probe=True`）：拉起、等窗口、再关闭自己拉起的那个实例。

`inventory_items()` 会过滤掉"确定不可用"的条目（`exe` 为空或 `launch_ok is False`），但 `launch_ok=None`（未做启动核验）的条目**会被保留**。因此清单语义是"**大概率可用**"，不是"已逐项验证可派单"。

### 6.3 上报到云端

`core/local_tools.py:365-406`：

- `report_agent(items, only_if_changed=True)` → `POST {cloud}/api/agent/inventory`，带配对 token；
- 每条上报字段：`name / launch(绝对路径) / version / path / summary / aliases / updatedAt`；
- 本地状态文件记录上次签名，**没变化就不重复上报**；
- `core/local_agent.py:121-141`：桌宠配对成功后挂上上报器，启动时强报一次，之后由 `local_tools.set_change_reporter()` 在扫描结果变化时触发。

云端 `cloud/server.js`：

- `POST /api/agent/inventory` 按 `agent.id`（设备）落盘 `inventory.json`；
- 每台设备最多保存 200 条工具，30 天未更新视为过期；
- 工具名统一规范化，匹配时对 `name/launch/aliases` 做**大小写不敏感的子串匹配**（`toolMatches`，`server.js:1533-1540`）。

### 6.4 跨设备派单时的核对

桌面端 `ui/comp_window.py:868-892` 会算出这次任务"必须装什么"：

1. **显式点名**：扫描 `app_registry.declarations()` 的 `name + aliases`，任务文本里出现哪个软件名，就把它加入 `requiredTools`；
2. **能力推导**：调用 `core/tool_router.required_tools(text)`，按能力表把"做 PPT / 写代码 / 查资料"推导成具体工具名；
3. 去重，最多 10 个。

然后拉取账号下的设备清单（`devices_inventory`），只列在线设备、显示已装工具、**不自动替用户选**。用户选设备后，`core/butler_cloud.py:290-333` 的派单请求同时带 `device` + `requiredTools`（最多 10 个）；服务端在真正派单前核对：

- 设备没有 inventory → `NO_INVENTORY`（前端提示"设备清单拉取失败"）；
- inventory 里缺某个工具 → `TOOL_MISSING`（前端提示"缺：XXX"）。

失败时**不降级到本机、也不换模型代写**——这条在 `ui/comp_window.py:841-850` 的跨设备分支里写死；错误码统一由 `core/butler_cloud.py:145-171` 翻成"缺哪个软件、可以换到哪台设备"的人话，而不是把 HTTP 400 原样抛给用户。

### 6.5 本机路由

`core/tool_router.route()`（`core/tool_router.py:65-166`）按任务能力选执行者，读取的仍然是 `local_tools.APPS` 的能力标签，**不是声明 JSON 的 `capabilities`**。所以改声明里的能力标签，不会改变本机派单路由；要改路由，得改 `local_tools.APPS`。

## 七、识别成功 ≠ 能用：派单阶段怎么暴露

"找到 exe"只是第一步。真实环境里最常见的三种"装是装了，但干不了活"：

### 7.1 未登录

- `app_registry.launch()` 拉起后，用 `login.signals`（窗口标题或 UIA 文本）判断是否停在登录页；命中返回 `login_required`，并附 `login.hint`（`app_registry.py:1076-1104`、`1495-1507`）。
- 豆包适配器在提交前还会再查一次登录文案，命中直接返回 `code='login_required'` 和下一步提示（`core/adapters/doubao_adapter.py:603-613`）。
- **WorkBuddy / JoyCode 没有独立的登录检测**，它们靠"找不到输入框/没有回执"间接失败；这是当前的真实缺口（见第 10 节）。

### 7.2 白屏

- 豆包：提交后若窗口内容长时间无变化，`_frame_blank()` 用像素方差判断空白；先尝试 `Ctrl+R`/重新打开自愈，仍空白才返回 `window_blank`，提示重启或检查网络（`core/adapters/doubao_adapter.py:596-605`、`904-930`）。
- WorkBuddy：没有"白屏"专用码；读不到输入框/回执会落到 `empty_answer`、`paste_failed` 等失败码。
- JoyCode：用"加载中的窗口标题"判断 `window_not_ready`，不是像素白屏检测（`core/adapters/joycode_ui.py:382-400`）。

### 7.3 停在编辑页 / 没选工作区

- WorkBuddy：`_ppt_editor_state()` 检测是否停在上一单的 PPT 编辑页；检测到就尝试"回主页 → 新建任务"自愈；自愈失败返回 `stuck_ppt_page`，并给出"点左上角第二个图标回主页，再重派"的具体提示（`core/workbuddy_bridge.py:558-564`、`700-730`、`1144-1155`）。
- JoyCode：没设置工作区时找不到工程，返回 `workspace_not_found`，要求用户在弹窗里手动选一次（`core/adapters/joycode_adapter.py:74-84`）。
- 豆包：提交后若停在登录页/对话页之外的页面，按 `failure_codes` 映射成明确失败码，而不是"等超时"。

### 7.4 谁来把失败说给用户

- 本机执行：`agent/guga_agent.py` 领单后、真正动键鼠前，由适配器自检；失败结果以 `{ok:false, code, hint}` 回报云端，任务不会被标成"完成"（`agent/guga_agent.py:291-340`）。
- 云端跨设备：在**派单时**就用 `requiredTools` + inventory 拦截，缺工具直接拒绝（`cloud/server.js:1249-1258`）。
- 桌面端：统一用 `core/tool_mandate.failure_message()` 把失败码翻成"下一步做什么"，并坚持"没有真实工具回执，不拿模型代写冒充"（`core/tool_mandate.py:138-160`）。

所以"派单阶段暴露"要分两个边界说清楚：

| 场景 | 暴露时点 | 机制 |
| --- | --- | --- |
| 跨设备（A 派给 B） | **派单前** | 云端 `requiredTools` 核对 B 的 inventory，缺工具直接 `TOOL_MISSING` |
| 本机（桌宠自己干） | **领单后、动键鼠前** | 适配器检查窗口/登录/白屏/编辑页，失败带 code+hint 回报，不假装完成 |

## 八、识别一条软件的全流程（以豆包为例）

```
用户说"用豆包写个周报"
        │
        ▼
tool_router.route() 读 local_tools.APPS 能力表 → 认为需要"豆包"
        │
        ▼
dispatch.adapter_for("doubao") 读声明里的 adapter → 加载豆包适配器
        │
        ▼
豆包适配器 _resolve_exe()
   ① 环境变量（声明 install.env）
   ② 常见目录（声明 install.common_paths）
   ③ （声明里写的单实例字段，实际读不到）
        │  没找到 → not_installed
        ▼
启动 exe → 等窗口 → find_window(title_keywords/process_names)
        │  没有窗口 → window_not_found
        ▼
检查登录页 → 检查白屏 → 找输入框
        │  登录页 → login_required
        │  白屏   → window_blank
        ▼
粘贴提示词 → 回车 → 等忙闲标记 → 读剪贴板
        │
        ▼
返回 {ok, text, evidence} 或 {ok:false, code, hint}
```

注意：这条链里**没有读 `app_reports.json`**，也没有读声明里的注册表/开始菜单/绿色版规则。  
声明驱动的完整探测链（第四节）在当前产品里主要服务于 MCP 接入状态判断与验证脚本，尚未成为豆包适配器的路径来源。这是第 10 节第一条不一致。

## 九、新机制：MCP 自报路径（目标口径与实现状态）

> 本节按"发现靠 MCP 自报、指挥靠界面自动化"的目标口径写。  
> 核心探测层已经落地，三家适配器的接入仍在实现中；**最终以代码为准**。

### 9.1 软件怎么自报

1. 用户在桌宠右键「🔌 目标软件接入」里复制 MCP 配置，粘到目标软件的 MCP 配置文件并重启；
2. 目标软件连上咕嘎的 MCP server（`core/adapters/guga_mcp_server.py`，`--guga-mcp` 启动）；
3. 软件调用 `report_app(app_id, name, exe_path, version, capabilities)`，自报：
   - 软件标识（`doubao` / `workbuddy` / `joycode`）
   - 显示名
   - **exe 绝对路径**
   - 版本
   - 能力标签
4. `core/adapters/app_reports.py` 校验：绝对路径、`.exe` 后缀、文件存在且非空；通过后**原子写** `%LOCALAPPDATA%\GUGA\app_reports.json`，并回读校验；
5. 同 id 再次上报会覆盖旧记录；升级换目录后再报一次即可。

### 9.2 咕嘎怎么用这条记录

`app_registry.probe()` 在用户指定之后、环境变量之前读取自报记录：

- 路径有效 → 直接返回 `source='mcp_report'`；
- 路径失效 → 写一条 `mcp_report_invalid` 警告，**继续按后面的来源探测**，不阻断；
- 自报记录的变化会让探测缓存指纹变化，自动重新探测。

同时，用户仍然可以手动指定路径，优先级始终最高；手动指定会写入 `runtime/app_registry_user.json`，并清掉缓存。

### 9.3 边界（必须背下来）

- **MCP 只发现，不指挥**：不通过 MCP 下发任务、不通过 MCP 收答案。
- **派活一律走界面自动化**：置前窗口、模拟键鼠、读剪贴板/工作区回执、逐步截屏取证。
- **MCP 连不上不影响派单**：连不上就回退声明 + 探测；不会因为 MCP 断开就罢工。
- **自报路径不是"永久真理"**：软件卸载/升级/移动目录后，咕嘎检测到路径失效会自动回退并记录原因。

### 9.4 实现状态（如实说）

| 环节 | 状态 | 证据 |
| --- | --- | --- |
| `report_app` 工具与落盘校验 | **已实现** | `core/adapters/guga_mcp_server.py`、`core/adapters/app_reports.py` |
| 探测链第 ② 级（用户指定 > MCP 自报 > 探测兜底） | **已实现** | `core/adapters/app_registry.py:1144-1170` |
| 自报失效回退 + 记录原因 | **已实现** | `mcp_report_invalid` 警告 + 继续探测 |
| 豆包适配器消费自报路径 | **未接入** | `doubao_adapter.py:755-780` 仍只读 env + common_paths |
| WorkBuddy 适配器消费自报路径 | **未接入** | `workbuddy_bridge.py:30-47` 仍用单一 `LOCALAPPDATA` 候选 |
| JoyCode 适配器消费自报路径 | **未接入** | `joycode_adapter.py` 仍走自己的环境变量/注册表/开始菜单扫描 |
| `mcp_channels.channel_status()` 使用探测链 | **已实现** | 用它判断 MCP 接入状态 |
| MCP 只用于发现的任务总线 | **未完全收敛** | `guga_mcp_server.py` 仍保留 `get_task/report_progress/submit_artifact/ask_guga` 四个任务工具（见第 10 节） |

## 十、声明与代码不一致清单（不圆）

以下均为静态代码核对结果，不是设计建议。按影响面排序。

1. **声明驱动的探测链没有接进日常派单。**  
   `app_registry.probe()` 实现了用户指定、MCP 自报、注册表、开始菜单、PATH、进程、绿色版全套（`core/adapters/app_registry.py:1118-1280`），但真正拉起软件的三条路——`core/adapters/doubao_adapter.py:755-780`、`core/workbuddy_bridge.py:30-47`、`core/adapters/joycode_adapter.py` 的启动扫描——都各自硬编码，不调用 `app_registry`，也不读 `app_reports.json`。  
   后果：声明里写再全，日常本机派单仍可能"找不到"；MCP 自报路径对实际拉起尚未生效。

2. **`capabilities` 不参与本机路由。**  
   声明里的 `capabilities` 只随探测结果返回（`app_registry.py:1105-1117`）；`core/tool_router.route()` 读的是 `local_tools.APPS` 的硬编码能力表（`core/tool_router.py:65-166`、`core/local_tools.py:36-81`）。改声明能力标签不会改变派单路由。

3. **`local_tools` 的注释说"注册表"，代码里没有注册表。**  
   模块注释写"先在开始菜单/注册表找到真实 exe"，但 `local_tools.py:122-128` 只有 `exe_globs` + 开始菜单 `_start_menu_target()` + `shutil.which()`，没有 `winreg`。  
   后果：绿色版/非默认盘/未登记开始菜单的软件，`local_tools` 识别不到；而 `app_registry` 能识别，但两者没打通。

4. **`local_tools` 的 `exe_globs` 与声明、执行器三张路径表不一致。**  
   例：豆包  
   - 声明 `doubao.json`：`%LOCALAPPDATA%\Doubao\Application\Doubao.exe` 等；  
   - `local_tools.APPS`：只有一条 `%LOCALAPPDATA%\Doubao\Application\Doubao.exe`；  
   - `agent/guga_executor.py` 的 `APP_PROFILES`：`Application\app\Doubao.exe` + `ByteDance\Doubao\...` + `D:\Doubao\...`。  
   WorkBuddy：声明写 7 条 + 注册表 + 开始菜单；`workbuddy_bridge.py:30-31` 只查 `%LOCALAPPDATA%\Programs\WorkBuddy\WorkBuddy.exe` 一条。  
   后果：同一台机器上一条链找到、另一条链找不到；换机器时表现随机。

5. **`launch.show` 与 `launch.single_instance` 声明了但代码不读。**  
   `app_registry.launch()` 固定 `SW_SHOWNOACTIVATE`（`app_registry.py:1376-1382`、`1458-1460`），并且只要已有窗口就返回 `already_running`（`1439-1445`），两个字段不影响行为。

6. **`ready.input_anchor` 当前实际未启用。**  
   三家声明都写 `must_exist: false`；`_input_anchor_ok()` 直接返回 `None`（`app_registry.py:1403-1415`）。所以"输入框在不在"这一层，声明驱动链没有真正检查。

7. **`login.required` 没有代码读取。**  
   是否报登录只看 `login.signals` 是否命中；`required` 布尔值不参与判断。WorkBuddy/JoyCode 也没有独立的登录检测。

8. **`receipt` 整块基本是文档。**  
   `receipt.mode`、`artifact_roots/globs`、`complete_rule` 在 `app_registry` 里不参与执行；WorkBuddy/JoyCode 适配器也不读声明，回执方式在代码里各自硬编码。豆包适配器读 `anchors.done/failure_codes`，但没读 `receipt`。

9. **WorkBuddy/JoyCode 的声明字段大量未被消费。**  
   `workbuddy_bridge.py` 与 `joycode_adapter.py` 都**没有 import `app_registry`，也没有读 `apps/*.json`**。两份声明里的 `anchors`、`receipt`、`login`、`channel.ui_steps` 主要是文档；真正生效的是代码里的常量。  
   只有 `adapter` 字段被 `dispatch.adapter_for()` 用来加载模块，`channel` 被 `mcp_channels.channel_status()` 用来展示接入状态。

10. **豆包适配器把 `single_instance` 读在 `install` 下，默认值却定义在 `launch` 下。**  
    `doubao_adapter.py` 读 `install.single_instance`，而 `_DEFAULTS` 把 `single_instance` 放在 `launch`（`app_registry.py:76-133`）。实际永远是 `None`，这段逻辑是死分支。

11. **只有 3 份声明，但 `local_tools` 能力表里还有元宝/智谱/Trae/Kimi。**  
    `local_tools.py:36-81` 里有这些条目，`core/adapters/apps/` 里没有对应 JSON。后果：
    - `app_registry.probe('元宝')` 返回 `unknown_app`；
    - 跨设备 `_cross_required_tools()` 扫描声明名/别名时**扫不到"元宝/智谱"**，用户点名也不会加入 `requiredTools`；
    - 但 `required_tools()` 又可能按能力推导出别的工具名，出现"点名元宝、实际核对豆包"的错位。

12. **Kimi 没从 `local_tools` 移除。**  
    README 写"Kimi 因付费门槛已移出适配名单"，但 `local_tools.APPS` 仍有 Kimi 的 exe 路径；`agent/guga_executor.py:645-649` 才把 Kimi 放进"排除/跳过"名单。  
    后果：清单可能上报 Kimi 可用，路由也可能选中它，但执行器不执行。

13. **`guga_mcp_server` 的定位与工具集自相矛盾。**  
    文件头写"MCP 只负责发现，不负责指挥"，但同一文件仍暴露 `get_task` / `report_progress` / `submit_artifact` / `ask_guga` 四个任务总线工具；`workbuddy.json` / `joycode.json` 的 `channel.ui_steps` 也在教用户点这些工具。  
    按新口径，这四个工具应与"只发现"边界收敛；当前实现仍可被客户端当作"领任务"通道。**这是目标口径与当前代码最大的口径差，文档不把它说成已完成。**

14. **`app_reports.py` 的注释说"适配器读它"，实际没有。**  
    模块注释写"适配器在拉起软件前读这条记录"，但豆包/WorkBuddy/JoyCode 三个适配器都没有引用 `app_reports`；只有 `app_registry.probe()` 读。

15. **跨设备 inventory 的"已装工具"不等于"已验证可派单"。**  
    `inventory_items()` 只过滤 `launch_ok is False` 和空 exe；`launch_ok=None`（没做启动核验）也会上报（`local_tools.py:321-345`）。所以设备清单显示"已装"，不代表没登录/没白屏/没停在编辑页。真正的可用性检查发生在本机领单后（第 7 节）。

## 十一、怎么复现这些结论

```powershell
# 1) 跑声明驱动探测（只读，临时缓存，不污染运行目录）
python scripts/verify_app_registry.py --json

# 2) 看本机工具清单与缓存（不启动软件）
python -c "from core import local_tools; import json; print(json.dumps(local_tools.inventory(), ensure_ascii=False, indent=2))"

# 3) 看 MCP 自报档案
type "%LOCALAPPDATA%\GUGA\app_reports.json"

# 4) 看探测缓存（含 source/elapsed_ms）
type "%LOCALAPPDATA%\GUGA\runtime\app_registry.json"
```

**一句话总结**：咕嘎找软件不靠猜——先听用户、再听软件自报、最后才按声明清单查注册表和开始菜单；找到 exe 只是开始，登录页、白屏、编辑页这些"装而不能用"的状态会在派单/领单阶段带着失败码暴露出来，绝不拿模型代写冒充回执。当前代码的短板也很明确：**完整的声明探测链和 MCP 自报还没接进三家适配器的实际拉起路径**，第 10 节已逐条列明。
